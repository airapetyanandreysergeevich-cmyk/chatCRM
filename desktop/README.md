# Локальная версия для Windows

Та же CRM, но без облака: программа держит базу у себя, а сотрудники с других
компьютеров подключаются к ней по локальной сети.

Один и тот же .exe умеет три режима — выбор делается при первом запуске и
меняется в настройках:

| Режим | Что делает |
|---|---|
| **Основа** | Держит базу и файлы у себя. Может раздавать их другим компьютерам мастерской. |
| **Клиент** | Только окно с интерфейсом; база на Основе в локальной сети. |
| **Online** | Только окно с интерфейсом; база в облаке. |

## Почему настоящий PostgreSQL, а не файловая база

Потому что в планах — синхронизация локальной базы с облаком и доступ к
Основе из интернета. Как только это появится, обе стороны обязаны быть одной и
той же базой: одна схема, одни миграции, одни правила изоляции. Файловая база
потребовала бы второй схемы (в SQLite нет массивов, нет построчной защиты), и
дальше каждая правка расходилась бы на две несовместимые версии.

Кластер создаётся в папке данных мастерской и слушает **только 127.0.0.1**.
Наружу база не выставляется никогда — сотрудники ходят в HTTP-API, где
работают права. Прямой доступ к базе означал бы, что разграничения нет.

## Как это собрано

Оболочка почти ничего не делает сама: поднимает базу, запускает бэкенд
дочерним процессом и показывает в окне тот же интерфейс, что и в браузере.
Интерфейс отдаёт сам бэкенд (`STATIC_DIR`), поэтому сотруднику с соседнего
компьютера достаточно браузера — программу ставить необязательно.

```
src/
  main.js       оболочка Electron: окно, трей, первый запуск
  setup.html    экран первого запуска: роль, папка, адрес Основы
  preload.js    мостик в окно — ровно пять действий, без модулей Node
  location.js   указатель на папку данных (в профиле пользователя)
  paths.js      раскладка папки данных
  config.js     config.json: режим, порт, пароли базы, копии
  postgres.js   создание кластера, запуск, остановка, роли и права
  backend.js    запуск сервера дочерним процессом и ожидание готовности
  bootstrap.js  подготовка Основы одним повторяемым проходом
build/
  installer.nsh правило брандмауэра при установке
test/
  local-db.js          проверка, что кластер настроен как облачный
  backend-lifecycle.js проверка запуска, падения и остановки сервера
```

## Папка данных

Выбирается при первом запуске. Внутри — всё, что наживает мастерская:

```
<папка данных>/
  db/        кластер PostgreSQL
  files/     фотографии заказов
  backups/   резервные копии
  logs/      журналы базы и сервера
  config.json
```

`config.json` содержит пароли базы, которые больше нигде не дублируются.
Потерять его — значит потерять доступ к собственной базе, поэтому он должен
попадать в резервную копию наравне с данными.

## Проверки

```
npm run check-backend
FINECRM_PG_BIN=/usr/lib/postgresql/16/bin npm run check-db -- /tmp/проба
```

Первая поднимает вместо бэкенда заглушку и убеждается, что оболочка дожидается
готовности сервера, замечает его падение и объясняет причину строкой из
журнала. Вторая создаёт настоящий кластер, заводит роли, ставит те же правила
изоляции, что в облаке, и проверяет, что роль приложения видит строки только
своей мастерской.

На Windows переменная `FINECRM_PG_BIN` не нужна: бинарники едут вместе с
программой, в `resources/pgsql/bin`.

## Что нужно для сборки установщика

1. `vendor/pgsql/` — распакованные бинарники PostgreSQL 16 для Windows x64
   (zip с сайта EnterpriseDB, папки `bin`, `lib`, `share`).
2. Собранные `backend/dist` и `frontend/dist`.
3. `build/icon.png` (256×256) — иконка программы и значок в трее.
4. `npm run dist` — на выходе `dist/FineCRM-0.1.0-setup.exe`.

Установщик просит права администратора один раз и добавляет правило
брандмауэра для порта 7373 в частных сетях.

## Чего ещё нет

- резервных копий по расписанию;
- поиска Основы в сети (mDNS) — пока адрес вводится руками;
- самоподписанного сертификата для локальной сети: трафик внутри сети пока
  открытый;
- подписи кода — без неё Windows встречает установщик предупреждением
  SmartScreen.
